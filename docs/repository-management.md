# 工作区、精选成果与版本管理

日常在 `experiments/<项目>/` 做实验，阶段完成后将报告、精选数据和仍需复用的少量配置归档到 `projects/<项目>/`。工作区整体忽略，不随 Git 或源码包分发；`projects/_template/` 是创建工作配置的模板。具体新建和续接命令见 [根 README](../README.md)。

## 哪些内容提交

| 内容 | 存放位置 | 提交 Git |
| --- | --- | --- |
| 候选、失败尝试与工作配置 | `experiments/<项目>/configs/` | 否 |
| 完整日志、预热、原始指标和遥测 | `experiments/<项目>/results/` | 否，另行备份 |
| 实验记录、分析草稿和临时汇总 | `experiments/<项目>/reports/` | 否 |
| 当前基线、仍需复用的候选及公共依赖 | `projects/<项目>/configs/` | 是 |
| 精选报告、小型逐次数据 | `projects/<项目>/reports/`、`data/` | 是 |
| 通用代码、测试、方法文档 | `src/`、`tests/`、`docs/` 等 | 是 |

**报告是阅读入口，配置是执行输入。** 报告应包含完整服务启动命令、镜像身份、CPU/GPU绑定、负载和压测协议，再给出逐次结果及限制。命令从解析计划或实际产物导出；已归档命令是当次快照，不跟随未来配置变化。

相同服务参数共用recipe，不为每个节点、并发或补测复制一套配置。节点资源差异在experiments内修改target；请求量随并发改变时仍按框架能力拆分workload。configs只维护当前基线和少量继续研究的候选，不引入继承系统来掩盖无价值的历史副本。

已结束候选可以移出当前configs：先确认报告记录了参数及测量条件，保存原始配置/结果，并将历史引用固定到对应Git commit。保留报告和CSV，不复制一份archive目录长期维护旧配置。保留的campaign仍需完整依赖，不能只剩无法执行的recipe片段。

失败不代表没有价值：普通试错留在工作区；影响后续研究的兼容问题或容量边界，在项目报告中保留结论，必要时附最小复现配置。不要把所有尝试都变成正式 campaign。

根目录已有的 results/reports 和本地归档保持原位，不改写历史记录。源码包不等于实验数据备份。

## 配置归档为什么可以正常使用

程序从 campaign 的父目录找到 `configs/`，所有 YAML 引用都相对于这个根。只改变外层位置、保留内部结构和内容时，`experiments/demo/configs/` 与 `projects/demo/configs/` 的解析结果相同。

| 内容 | 归档时怎样处理 |
| --- | --- |
| campaign 的 YAML 引用 | 保留内部路径；如果重命名文件，同时修改引用 |
| model/runtime/client/target/workload/recipe | 复制选定 campaign 的全部依赖，不跨配置根引用 |
| 自定义日志 JSON | 连同 `configs/logging/` 的所需文件复制；复现前运行 `prepare_logging.py` |
| 模型路径、本机地址、缓存根目录 | 仍按配置使用，不随 configs 自动改变；换机器须核对 |
| JIT 缓存 | 外层目录不参与缓存键；同镜像、模型 ID、GPU 架构、recipe 和 cache_root 下路径不变 |
| 报告和数据中的路径 | 检查相对链接；本地原始日志位置明确标注，不当作 GitHub 可访问链接 |

不要只复制 campaign，或使用指向 `experiments/` 的软链接代替依赖。归档后在 `projects/` 路径重新执行 validate/plan，确认参数与实测配置一致。它们检查配置和命令，不替代镜像、硬件或模型的实机验证。

recipe 的说明文字也参与缓存指纹，修改它可能产生新缓存目录；仅移动外层目录不会。整理时保留已验证字段，既有缓存不删除。不同项目允许独立复制少量依赖配置，避免修改一个项目时改变另一个项目。

## 冻结与提交

运行前固定公共代码版本、镜像、模型、完整工作配置和命令。**工作区被 Git 忽略，commit 和 git diff 无法记录其中的配置**；执行器会保存解析后的 YAML，完整 configs（包括日志 JSON）仍需随原始结果另行归档。

运行期间不改源码或配置，每次使用新结果目录。归档采用复制，保留原始工作配置和结果，不回写历史运行身份。实验工作区不覆盖原始配置；当前精选基线可在确认后更新，历史由报告、运行快照和Git版本保存，不要求永久维护全部旧执行入口。

日常在 `main` 上提交即可；需要隔离较大改动时再建临时分支。公共修复与项目成果保持清楚的提交边界，不为每个项目维护长期分支。

## 多台机器协作

各机使用同一公共 commit 和明确的配置快照，再核对本机 target。工作区不随 git clone 分发，需要从精选项目创建，或另行同步指定的冻结工作配置；只同步 Git 不能保证候选参数一致。

先校准约定的 baseline，再同时报告绝对性能和相对同机 baseline 的变化。校准阈值提前约定，优胜方案按计划复核。当前执行器只做本机实验，跨节点部署和 PD 编排尚未实现。
