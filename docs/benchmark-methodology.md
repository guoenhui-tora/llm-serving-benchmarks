# 压测协议

**新协议版本为1，适用于预热后服务的初筛、配置对比与稳定性检查；不替代冷启动或长期线上可用性测试。** 未指定 `measurement.protocol` 的旧配置保持原行为与指纹，不追溯接纳旧预热或被拒绝样本。

先确定实验要回答的问题，再确定最小测试范围。镜像选型、拓扑筛选、稳定性排查和容量探索应各有明确变量，避免一轮同时改变太多条件。

## 运行前固定什么

记录模型/tokenizer、镜像 tag 与实际 ID/RepoDigest、Git commit 和本地差异、解析配置及启动命令。相同 tag 不保证内容相同；CLI 存在也不代表模型、量化格式和 GPU 支持该路径。

核对 GPU、驱动、显存、PCIe/NUMA、功耗限制及其他计算进程。所选 GPU 已被占用就报告阻塞，不终止其他任务。已规划的同机多服务必须使用互不重叠的 GPU，并记录共享 CPU、内存和功耗条件。对 CPU 亲和性权限问题，优先评估容器权限和进程绑定，不修改宿主全局设置。

官方 recipe 是起点。记录来源 URL、访问日期、适用硬件和版本，再核对固定镜像的 CLI/实现。SM120 与 SM100 都属于 Blackwell，但 kernel、NVLink 和通信能力不同。

启动前与测量期间都要观察后台 CPU 负载，包括服务/客户端物理核及其 SMT 兄弟。Docker cpuset 只限制本次进程，不会排除其他任务。结合整机/逐核忙碌率、进程或线程采样，必要时检查相关 cgroup 的 CPU 增量；进程列表未显示异常不代表资源没有竞争。若背景负载在重复之间或测量途中改变，标记受影响窗口并分开解释，不能因 gate 通过或 CV 较小就当作条件一致的对照。用户接受残余负载后可按约定继续，但报告仍需保留其限制。

## 功能探测与性能测量分开

先 validate、plan、preflight，再检查 health、models 和简短生成。对支持 thinking 的模型，使用该模型实际支持的请求参数关闭 thinking，限制探测输出；不要把长思考误判为服务故障。

smoke 只证明功能可用。正式 recipe 应保留正常图优化、编译和可用 backend。短输入通过，不代表 8K/1K 能在相同并发下承载。输入加输出必须在上下文上限内。

## 选择协议与预算

同一case只启动一次服务，依次运行各workload和并发。并发C是客户端最大在途请求数；服务端活动序列容量是另一项固定配置。双实例的C、请求数均为整机总量，按既有同步机制等分。

| 协议 | 预热 | 接纳与结束条件 | 默认预算 |
| --- | --- | --- | --- |
| `quick` 快速测试 | 固定1轮，每轮2C请求；可显式改为2轮 | 接着固定测3轮，全部保留并标记事件，不补测 | 1轮预热＋3轮正式测量 |
| `jit_clean` 无JIT验收 | 没有独立预热阶段 | 每轮完整正式工作量；累计最先通过检查的3轮 | 最多12个完整轮次 |
| `stable` 稳定性确认 | 没有独立预热阶段 | 首次连续3轮通过事件检查，且指定指标达到阈值 | 最多12个完整轮次 |

新实验默认选择建议为 `jit_clean`，但配置必须显式填写 `protocol`。默认接纳3轮，可用 `repetitions` 显式增加到更多轮；稳定性窗口随之增大。每轮正式请求量始终取 `traffic.requests`，不会自动改成4C。本项目常用C32=128、C64=256请求；请求量随并发变化时拆分workload。快速预热的2C不等于正式4C，预热数据不进入正式统计。

`jit_clean` 遇到事件只拒绝本轮，已有样本不清零；`stable` 则重置连续窗口。两者下一轮直接继续完整工作量，不关服、不额外插入两轮预热。请求和token数、绑定及同步检查沿用原实现；OOM、请求失败、token数错误、服务异常按故障处理，不能作为普通预热盲目重试。

每个新协议必须配置 `budget_s`，按一个配置、一个workload、一个并发分别计时，包含该组客户端初始化、压测和检查，不含模型启动及最终清理。轮数或时间预算先到先停；剩余时间会限制客户端阶段超时，正在运行的客户端可能因此被终止，仍保留日志。清理和取证可以略超预算。轮数用尽或在轮次之间到达时间预算时，该组标为PARTIAL，同一服务继续后续workload。如果时间上限中止了正在运行的客户端，则结束并清理本case，避免残留请求污染后续负载；其他运行故障按FAIL处理。全部结束时统一清理本次服务。预算不足不自动重启重试。

### 稳定性阈值

`stable` 默认同时检查输出吞吐、Mean TTFT和Mean TPOT，三者必须都是有效正数，并满足：

```text
相对极差 = (窗口内最大值 - 窗口内最小值) / 窗口内均值 ≤ 0.02
```

2%是本仓库起点，不是通行标准；显式设置 `stability_threshold: 0.01` 可改为1%。它不是CV。窗口内有事件时重新累计；均无事件但未达到阈值时，按时间顺序滑动检查最近三轮，不能从历史中挑三个接近值。P95保留但不参与停止判断。

必须同时报告全部无事件轮次的统计和最终选中窗口。选中窗口的低波动不能代表整个运行过程稳定，更不能证明两配置1%的差距可靠。累计无JIT协议则不根据性能挑选；取得三轮后如实报告波动，明显不稳定时另行诊断，不不断补到满意。

### 结果与产物

每档目录为 `trials/<workload>/cXXXX/`，保存 `workload.json`、`protocol.json`、`measurement-XX/`；快速协议另有 `warmup-XX/`。`protocol.json` 逐轮记录事件数、指标、接纳序号、连续窗口判断、已用时间、停止原因，以及全部轮次、全部无事件轮次和选中轮次的逐指标均值/样本标准差。原始日志、raw/metrics、绑定与同步证据仍各自落盘。中断或故障保留已完成轮次，不提供自动恢复或跨启动拼接。

`bench report`展示轮次时间顺序和协议摘要，统计按协议及版本分组。PARTIAL组的已有样本保留在协议记录中，不进入正式组均值；同case内已完成的其他新协议组仍可汇总。FAIL/INTERRUPTED case保持不进入正式统计。CSV导出追加协议、版本、事件数和原轮次；快速测试标为QUICK_COMPLETE，不能冒充无事件PASS。

PASS只表示所选协议执行条件满足：quick可能含事件；jit_clean不保证性能收敛；stable仅表示选中窗口达到阈值。自动检查不证明没有后台干扰，正式归档前仍须审阅资源时间线和完整服务日志；不把人工审阅描述成已实现的自动资源gate。

### 旧配置兼容

未填写 `protocol` 时仍使用 `warmup_requests`、`min_warmup_rounds`、`max_warmup_rounds`、`max_attempts` 和 `repetitions`：每次重复／重试前独立预热，预算失败结束case。历史配置与已归档结果保持不变。采用新协议时新增workload/campaign，不覆盖正式历史文件；新旧协议字段不能混写。

## JIT观察边界

保留磁盘JIT缓存。前缀缓存与编译缓存是两回事：关闭prefix/radix cache不要求删除JIT缓存。固定请求长度也不能固定所有调度shape；相同磁盘缓存不代表每个worker都已加载，有限HTTP轮次不能保证穷尽所有形状。

现阶段三套协议复用原事件识别规则，没有放宽正则。真实编译、首次缓存加载以及延迟日志可能触发同一规则；无法精确归属时保守保留。事件数是日志匹配数，不是独立编译次数。日志窗口包含客户端初始化及日志刷新，不严格等于客户端计时区间；修正归属需另行保存证据和验证正反例。

| 看到的现象 | 如何处理 |
| --- | --- |
| TileLang/Triton 等编译事件 | 保留时间窗口；按规则继续预热或拒绝该次测量 |
| FlashInfer autotune 开始/进度 | 计入调优事件；完成日志本身不代表又开始调优 |
| “No tuned config covers” 后的调优建议 | 属于 fallback warning，不应仅因出现 tuning 字样就认定开始调优 |
| 缓存加载或进程内 cache miss | 不直接等同于实际 CPU 重编译；需要更具体日志或调用栈 |
| 日志没有任何事件 | 只说明观察规则未识别事件，还要看重复测量和资源状态 |

DSV4 排查中，安静日志曾漏掉 TileLang 活动。vLLM 0.29.0 的 `--jit-monitor-verbose` 提供了更多证据；SGLang 使用自定义 INFO 配置、`FLASHINFER_JIT_VERBOSE` 和编译器日志。变量名存在不代表所有相关日志都可见，要先验证 logger 级别和输出路径。这些参数并非跨版本通用。

自定义日志文件必须真实存在于容器可见路径。记录其内容/哈希；不能只在 recipe 中声明环境变量。缓存目录可能随 recipe 指纹变化，准备步骤必须按当前 recipe 计算路径，不能写死旧目录。

## 测量与结果验收

固定客户端、协议、tokenizer、长度、采样与请求量。缓存关闭实验显式禁用 prefix/radix cache。使用 `request_rate=inf` 时，通过最大并发限制在途请求；DP 部署的并发是全服务总量，不能在每个副本再乘一次。

每次核对成功数、失败数、实际输入/输出 tokens。固定输出且 `ignore_eos=true` 时，应满足 `输出总量=成功请求数×目标输出长度`；不能用提前 EOS 的数据声称更高吞吐。输入也要核对，不只看请求参数。

预热、事件轮次和接纳测量分别记录。无JIT及稳定性协议不接纳事件轮次；快速协议保留全部正式轮次并明确标记，不能混入无JIT结论。不按快慢挑样本。框架的 PASS 表示规定检查通过，不代表性能已收敛、所有 kernel 已验证或模型质量合格。

同配置、同并发的三次有效重复用于报告均值和样本标准差。初筛只有在服务配置、客户端、负载、请求数和代码一致时才能计入。吞吐稳定不代表 TTFT 稳定，各指标分别判断。

TTFT 是首 token 延迟；TPOT 是首 token 后的平均每 token 耗时；ITL 是流式事件间隔统计，需核对客户端分块和 token 计数定义。P95/P99 的重复均值不等于合并请求后的分位数。普通单服务模式仅保存汇总，无法恢复合并分位数；显式 `replica_targets` 模式保存逐请求延迟和流式事件间隔，可在同一次测量内合并各侧记录。流式事件不一定与模型 token 一一对应。

多实例必须同步测量，整机吞吐按共同计时窗口计算，不能直接相加两个各自窗口的吞吐。保留每侧结果、起跑时差与重叠时间，并明确是固定分流还是动态负载均衡。具体协议见[同步多副本部署](configuration.md#同步多副本部署)。

## 波动明显时先排查

按这个顺序检查，而不是不断重跑到满意：

1. 对照测量窗口，查 JIT/autotune、fallback、错误及服务停顿；必要时再取调用栈或短 profile。
2. 查 OOM、KV 容量、抢占/重算及调度等待。显存用得满不等于 KV 足够。
3. 查外部任务、温度、功耗、频率和 NUMA/通信回退。低频采样不能排除短暂干扰。
4. 查客户端瓶颈、连接/流式行为、实际工作量和统计窗口。
5. 明确原因或剩余不确定项后，再决定一次有目的的验证。

编译/观察问题与性能差异分开处理。规则误判时保留反例并做回归验证，不能放宽正则、隐藏 warning 或延长上限只为获得 PASS。若超过约定上限，记录阻塞和容量边界。

## 控制成本并保存证据

拓扑/参数筛选优先小范围。快速初筛使用quick固定预热后测三轮；正式对比用jit_clean，重点候选再考虑stable。不自动扩成所有并发的全矩阵。

确定测三次的配置，在同一次启动中完成；新协议不在每个合格样本前重复预热。这衡量预热后持续 serving 的波动，节省加载、Graph捕获及进程初始化时间。独立重启重复用于检查启动之间的差异，例如 autotune 选择或缓存装载差异；它不是天然更真实，也不要求删除磁盘 JIT 缓存。只有实验目标包含启动差异时才另设这类对照，不与同次启动的重复混用。

多台机器先用同版本 baseline 校准，再同时比较绝对性能和相对本机 baseline 的提升。相近 baseline 不能消除拓扑与硬件的交互影响，优胜方案仍应同机复核。

记录完整日志、实际 backend、重要 fallback、量化与 KV 路径，以及无法确认的项目。短中文回答正确不能替代质量评测。结束后清理本次容器，保留原始结果、源码/配置证据和缓存。
