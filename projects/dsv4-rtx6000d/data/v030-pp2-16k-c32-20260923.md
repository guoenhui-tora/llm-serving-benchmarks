# vLLM 0.30：DSV4 启动、补丁取舍与四卡 PP2 实测

**45 节点四卡 TP2 PP2、EP on、DSpark K5 已完成真实 16K/1024、C32 quick：输出吞吐 622.37±17.21 tok/s，384 条正式请求全部成功，三轮正式均无已知 JIT 事件。** 本次只加载 MXFP4 草稿量化分派修复及其加载核验代码，没有加载旧 DP 补丁、mHC 自定义 worker 或 top-k／草稿输入定向预热。

v0.30 已解决核实过的 mHC 预热入口缺陷，并包含旧 DP profiling 回移对应逻辑；MRV2 的 PP2＋DSpark 路径已在本配置实测跑通。当前 NVIDIA 0731 权重的 **MXFP4 草稿误走 NVFP4 分派仍需本地修复**。这不等于审计了 v0.29 的所有问题，也不证明所有 DP2、其他容量或冷缓存场景都无需补丁。

相对历史八卡双服务实验的平均四卡贡献 595.64 tok/s，本次吞吐约高 **4.49%**，TTFT 约低 **21.34%**，TPOT 约低 **1.22%**。该比较跨节点、版本、拓扑和预算；本次吞吐仍逐轮上升，不能据此认定 v0.30 或 PP2 带来稳定加速。

## 1. v0.29 → v0.30：哪些问题解决了

| 项目 | v0.29 问题或本地措施 | v0.30 的证据及本次处理 | 结论范围 |
| --- | --- | --- | --- |
| mHC 原生预热入口 | 旧 `_find_first_mhc_layer` 要求真实 NVIDIA 层没有的 `hc_pre/hc_post` 属性，导致漏掉预热；本地 worker 补入口 | [上游 #50178](https://github.com/vllm-project/vllm/pull/50178) 改为实际模型的 JIT 注册机制；本次 4 个 worker 原生 mHC 预热完成，HTTP／正式阶段没有 mHC 事件 | 已核实入口修复；不用旧 worker。更广 shape 覆盖仍取决于负载 |
| MRV2 的 PP＋DSpark 路径 | 旧项目 DSpark 实验路径受 PP 限制，未形成对应可用基线 | v0.30 有 PP、辅助状态转发及 PP 安全草稿加载实现；本次 TP2 PP2 GPU 实测通过 | 本配置已跑通，不外推其他 PP 切分 |
| DSpark DP profiling token 混用 | 曾回移 [#54856](https://github.com/vllm-project/vllm/pull/54856)，处理 dummy profiling 的跨 DP token 统计 | 实际镜像对应 `dummy_run`／`skip_attn` 分支已传 `num_tokens_across_dp=None`，没有再加载旧回移 | 源码已核对；本次 DP1 不能验证完整 DP2 路径 |
| MXFP4 草稿被按 NVFP4 加载 | 草稿独立 quant config 的惰性属性又读取主模型 NVFP4 上下文 | 实际 CUDA 注册表及 EngineArgs→DSpark loader 配置链复现误分派；最小补丁为草稿独立副本固定 MXFP4 专家格式 | **仍未解决，当前权重需要补丁**；目标模型 NVFP4 不变 |
| top-k／草稿输入等定向预热 | 为实验容量、指针对齐和输入 shape 主动覆盖 JIT；不是每一项都属于源码 bug | 本次不加载，正常一轮 warmup 中出现 19 条事件，正式三轮为 0 | 此负载没有证据需要加回来；不保证冷缓存、其他容量无 JIT |
| CUDA Graph 覆盖 | K5 扩容后若仍沿用小捕获上限，会失速，即使日志 0 JIT | 本次容量 32，目标验证 32×6＝192、草稿 32×5＝160，配置捕获上限 192 | 仍需随每引擎容量配置，升级不会替用户自动修正所有旧 recipe |
| attention CLI 字段 | 旧 `use_fp4_indexer_cache=false` | v0.30 删除该字段，本次使用 `indexer_kv_dtype=auto` | CLI 适配，不是额外 kernel 补丁 |
| 启动等待超时 | 前序无补丁 TP2 DP2 尝试在 API 内部默认 600 秒退出，且有草稿 scale 警告 | 本次显式内部 1800 秒、外层 READY 2100 秒，成功启动实际等候 97.27 秒 | 等待预算配置；不能把前序失败视为已完成的 DP2 验证 |

源码审计固定 v0.30 commit `ced6857afa0ea7b2e3f0846a62e1394e90f15607`；执行以以下镜像身份为准。旧补丁背景见[DSpark 兼容性记录](../reports/dspark-compatibility.md)、[mHC 扩展](../patches/mhc-startup-warmup-extended/README.md)与[输入内核覆盖](../patches/input-kernel-warmup/README.md)。

## 2. “一轮 warmup”到底包含什么

实际顺序为：**启动服务（vLLM 自动完成内部准备）→ 一轮 64 请求 warmup → 三轮各 128 请求正式测试**。没有额外手动执行定向 kernel 预热脚本，也没有第二轮 HTTP warmup。

- 启动内部准备：模型加载、vLLM 原生 kernel 预热及 CUDA Graph 捕获，属于服务启动过程，不是一次额外的压测轮次。
- HTTP warmup：服务 READY 并通过简短功能探测后，通过 `/v1/completions` 发送真实负载，即通常说的“一轮 warmup”；本次 C32、64 条完整 16K/1024 请求，独立保存，不计入正式均值。
- 保留并复用了前序同版本启动生成的磁盘 JIT 缓存。本次不是清缓存后的冷启动，不能用 97.27 秒作为冷启动时间，也不能保证全新缓存只需相同预热成本。

warmup 匹配事件：`ComputeGlobalTopkIndicesAndLensKernel.kernel` 16 次、`_prepare_dflash_inputs_kernel` 2 次、`_resample_kernel` 1 次。计数包含 worker／特化及可能延迟的日志，不等于 19 个不同 kernel。没有 HTTP 阶段 mHC 事件。

| 压测客户端 | 固定原 vLLM 0.29.0 客户端，与历史保持一致；服务端为 0.30.0 |

当前 checkpoint 的主模型 routed experts 是 **NVFP4**，3 个 MTP 草稿层的专家是 **MXFP4**，不能因目录名含 NVFP4 就假定全部专家格式相同。补丁校验 3×256×3＝2304 个草稿矩阵的 safetensors 头：packed I8 权重、E8M0／group32 scale，缺少 NVFP4 的 `weight_scale_2`／`input_scale`。这不是 MXFP4→NVFP4 转换。

实际使用的[补丁及核验测试](../patches/v030-dspark-mxfp4/README.md)已随本报告归档，文件与成功运行版本逐字节一致。它通过 `sitecustomize.py` 的 import hook 修改固定 DSpark loader 的草稿量化赋值，保留 FP8 线性层和目标 NVFP4，并检查镜像源码、模型 config/index 的哈希。v0.30 CUDA 实际注册类来自 `deepseek_v41.quant_config`，不能照搬仅检查 CPU fallback 的 `deepseek_v4` 类型判断。

补丁还检查末级两个 worker 上真实加载的各 3 个 MoE 模块，输出 `LOCAL_DSPARK_LOADED`：必须是 `Mxfp4MoEMethod`、kernel 已初始化，本次后端为 `DEEPGEMM_MXFP4`；目标后端为 `FLASHINFER_CUTLASS`。PP 下原生 `info_once(scope="local")` 不在草稿所在末级输出，因此增加实际对象证据，保留原有 scale 错配和异常 gate。

## 4. C32 quick 结果

数据为 GovReport 前缀池 `govreport-16k-prefix-1024-v2.jsonl`，SHA256 `025246b18d8ba7e1bc4d98c1a20b32b570860bb06a0baf0cea4ae97403d982e7`。每条输入精确 16384 tokens、输出 1024；不是仅设置上下文上限 16K，也不是共享前缀 decode-only。数据制备入口见[数据集说明](../datasets/README.md)。固定前 N 条、C32、request rate＝inf、temperature0、seed0、ignore_eos，关闭前缀缓存。

每轮正式实际输入 2,097,152、输出 131,072 tokens。正式草稿计数为 573,910 个候选 tokens、278,612 个接受 tokens、114,782 次草稿轮次；平均接受长度 3.4273，包含额外目标 token。短功能请求通过，不替代完整生成质量评测。

**607→618→641 的上升没有已观测 JIT 支持，原因尚未确定。** 接受率相近，TPOT 逐轮下降；CPU 调度背景、GPU 运行状态或批次组织均未完成因果验证。吞吐 CV 2.77%、相对极差 5.42%，属于 quick 通过，不是 stable。保留全部三轮，不只取 641，也不追加到满意为止。

无 OOM、无 scale 错配警告、无抢占日志；KV 日志峰值 29.4%，服务最大 running32。主模型阶段约 40.05 GiB/卡，末级含草稿约 44.26 GiB/卡。保留 SM120 SymmMem 不支持、TP2 FlashInfer All Reduce 不可用、NCCL P2P 初始化等 warning。宿主仍有 8 个 DOCA 后台 CPU 进程，资源采样不足以排除瞬时干扰。

成功运行时间为北京时间 2026-09-23 22:09:42–22:27:00。只有一组成功性能测试；此前依次发生缓存元数据权限预检查失败、补丁误用 CPU fallback 类型、PP 原生后端日志缺失、补充 INFO 日志被过滤。前者未启动模型，后三者未做 HTTP 测量；总计 4 次 GPU 模型启动，修正的是准备／补丁封装／观测，不是多组性能里挑最快。所属容器已清理，磁盘缓存保留。

## 5. 与历史真实 16K 四卡贡献比较

历史来自 2026-09-21 [八卡普通双服务实验](../reports/pd-dspark-16k-c32-c64-20260921.md)的 **OR-C64**：46、48 各一个四卡 TP2 DP2、EP on、K5 服务，经代理承接全系统 C64。已重新读取逐请求路由和客户端记录，确认每个服务最大在途为 32，三轮分别分到 128／128、128／128、130／126 条请求。

| 配置 | 四卡输出吞吐贡献 tok/s | Mean TTFT，s | Mean TPOT，ms |
| --- | ---: | ---: | ---: |
| v0.29，46 节点，TP2 DP2 | 598.73 | 6.291 | 45.53 |
| v0.29，48 节点，TP2 DP2 | 592.55 | 6.171 | 46.64 |
| **v0.30，45 节点，TP2 PP2，本次独立 C32** | **622.37** | **4.901** | **45.52** |

历史每轮四卡贡献＝该服务实际输出 tokens／当轮八卡客户端完整测量时间，再对三轮取平均。延迟按该服务实际请求计算后逐轮平均；不使用服务自身较短的结束窗口放大吞吐。历史八卡总吞吐 **1191.29 tok/s**，两服务平均贡献 **595.64 tok/s**；它们是同一次八卡实验的拆分统计，**不是两个独立单四卡 C32 测试**。

本次相对平均贡献高 4.49%；TTFT／TPOT 的变化以历史 OR-C64 三轮全体请求指标均值为分母，分别为 −21.34%／−1.22%。[拆分逐轮 CSV](v030-pp2-16k-c32-20260923-historical.csv)及[计算值、输入文件哈希](v030-pp2-16k-c32-20260923-comparison.json)可追溯该换算。

比较限制必须同时保留：

- 同模型、数据池、输入输出长度、K5、EP on、客户端版本、prefix cache off；但历史取前 256 条动态分流，本次前 128 条，分给某个服务的文本不是完全相同。
- 历史是两服务全局 C64 的动态分流，单服务观察到最高 32；本次是独立服务 C32，调度和收尾不完全等价。
- 历史每 DP 引擎容量 32、budget16384（每四卡服务 2 引擎）；本次 PP 服务容量 32、budget8192，节点、并行通信、版本和 CPU 背景也不同。
- 历史每档 256 请求完整 warmup，本次 64；旧版启用本地定向预热，新版没有。两边均保留磁盘缓存。
- 没有同机同协议 v0.30 DP2 或 DSpark off 对照，不能分离版本、PP 或投机解码的收益；4.49% 小幅差距仍需复核。

其他历史“16K”可能指 max-model-len，实际输入约 8K；共享前缀 16K decode 参照命中率约 98.44%。这些不进入本表，也不把 PD 八卡总吞吐拿来与本次四卡直接排名。
