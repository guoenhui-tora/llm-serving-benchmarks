# DSV4 / RTX 6000D: v0.30 单批次 24 卡 4P2D decode 容量扫描

## 结论与适用范围

在 `gpu-6000d-46/47/48` 各八卡、四个独立四卡 P 加两个独立四卡 D、全服务 TP2×DP2/EP on/DSpark K5 的**同一次启动**中，用真实 GovReport 精确 16K 输入/1024 输出完成了全局 C16～C144 步长 16 的扫描，并按事前规则追加 C160。必测锚点 **C64 为 2680.39±14.17 output tok/s**、**C128 为 3930.44±18.39**；三个正式轮次的样本标准差见下表。C144 为 4120.98±8.80 tok/s，C160 再高 3.46%，达到 4263.74±35.61；但 C160 Mean TTFT **11.898 s > 10 s**，Mean TPOT **23.355 ms < 50 ms**，因此**首次触及 TTFT 停扫线的是 C160**，不测 C176～C256。C144→C160 的联合 SLO goodput 从 3.167±0.037 降至 2.339±0.408 req/s，下降 26.17%；不能只按吞吐选择 C160。

按**相同全局并发/GPU**对齐历史工作点：12 卡 2P1D/C64 → 24 卡 4P2D/C128（每卡 5.33）吞吐 **2.02 倍**；16 卡 3P1D/C96 → 24 卡 4P2D/C144（每卡 6）吞吐 **1.60 倍**。两项历史比值均未显示明显低于 GPU 数量的同比例增长，但旧组使用 vLLM 0.29 与不同客户端/数据、D 容量及 P budget，**不能将近线性扩展归因于 4P2D 本身，也不能据此断言其对 16K 最优**。具体对齐条件和逐请求质量见下方历史对照。

本次只有**双四卡 D 的 4P2D**获得完整扫描。[单节点 decode-only 对照](../docs/decode-only-8gpu-20260925.md)的同一 C128 共享前缀负载中，双四卡 D 优于八卡单实例，因此依据预定决策规则**未部署单八卡 D**，也没有运行独立 2P1D、`2×(2P1D)` 或其他 P/D 配比。decode-only 的共享前缀与这里的语义输入、PD 远端 KV 路径不同，两个实验的绝对吞吐不能直接排名。本批只是一组服务启动内的 quick 重复，不证明跨启动稳定性或 24 卡最优拓扑。历史[3P1D v0.30 报告](v030-pd-16k-dp2-20260924.md)客户端仍为 v0.29，且数据集不同，不能与本批直接做纯拓扑或客户端版本归因。

### 复现方法与限制

同一实验机上，先核对当前节点授权和 GPU 空闲，不清理他人容器；核对 46/47/48 各自 image ID、权重/项目数据 SHA、GPU–NUMA–CPU 映射、RDMA NIC 与本表端口。45 只运行控制/代理/客户端。核对[固定配置快照](../data/pd24-20260925-commands/plan.json)以及六个服务、代理和客户端 argv 中的主机路径、缓存挂载、模型补丁和 client JSONL 选项；异机部署必须改本机相关路径，不能仅复制 Docker 命令。原脚本继承本机上一轮 v0.30 G2 `resolved.json`，并从各节点已有 JIT 缓存分出含 MXFP4 修复和 `pd-logging.json` 的新目录；它们是**工作区/宿主前置依赖**，本次没有把旧原始运行目录和缓存内容提交为项目配置。

在上述依赖齐备且本机 `experiments/dsv4-pd-24gpu-20260925/` 的原始编排脚本和 `results/plan.json` 尚在时，以下命令依次只读验证已准备的快照、做实际节点预检，然后使用**新**的 run-root 运行；`preflight` 会做 Docker CLI 检查，`run` 才会启动服务、预热和测量。原脚本第一次建立新工作区时先运行 `prepare` 生成冻结 `plan.json`，已有 plan 不可覆盖；重新做 campaign 须调整工作区、owner、源配置、缓存和预算快照，并重新验收，不能照抄本次 owner 或复用既有 run-root。

```bash
PYTHONPATH=src python3 experiments/dsv4-pd-24gpu-20260925/scripts/run.py offline
PYTHONPATH=src python3 experiments/dsv4-pd-24gpu-20260925/scripts/run.py preflight
PYTHONPATH=src python3 experiments/dsv4-pd-24gpu-20260925/scripts/run.py run \
  --run-root experiments/dsv4-pd-24gpu-20260925/results/pd24-repro-01
```

实际执行严格按照归档计划先 C64/C128、再补齐 C16～C144，C144 后按 **Mean TTFT>10 s 或 Mean TPOT>50 ms** 判断是否继续至多 C256；预热与每轮原始结果独立保存，owner 清理只针对本批六服务。上述命令是**复现入口说明，不是本次又运行了一轮**；此处的 `experiments/` 被 Git 忽略，新克隆缺少旧 G2 `resolved.json`/JIT 缓存/本地脚本，不能直接执行。可以用已提交的命令快照、数据集、逐轮 CSV 和报告核对参数与预期工作量，再移植这些前置依赖。原始当次完整 `run-root` 仅本机可用。

## 同每卡并发下的历史扩容参照

这里的 C 始终是**整机全局并发**；按 `C/总 GPU 数` 选匹配点，而不是固定全局 C64 来要求 GPU 翻倍后吞吐翻倍。`C/GPU` 只是客户端配置的名义平均在途数，**不是实测逐卡 decode batch**。比较双方都用完整客户端窗口、真实精确 16K 输入/1024 输出、TP2×DP2、EP on、DSpark K5、远端 KV、关闭本地 prefix cache、三轮 quick；不同批次的请求文本及软件栈仍有差异。吞吐均值±三轮样本 SD，goodput 为逐请求 TTFT≤10 s 且 TPOT≤50 ms 的达标请求/完整窗口。

| 资源与部署 / 来源 | 全局 C / C÷GPU | output tok/s | 每 GPU tok/s | Mean TTFT / TPOT | goodput req/s / 联合达标率 |
|---|---:|---:|---:|---:|---:|
| [12 卡 2P1D，历史 v0.29](pd-night-20260922-execution.md) | 64 / 5.33 | 1942.67±26.41 | 161.89 | 9.870 s / 20.796 ms | 1.468 / 77.34% |
| **24 卡 4P2D，本批 v0.30** | **128 / 5.33** | **3930.44±18.39** | **163.77** | **8.104 s / 22.431 ms** | **3.136 / 81.71%** |
| [16 卡 3P1D，历史 v0.29，Graph288](pd-16k-graph-capacity-20260923.md) | 96 / 6.00 | 2582.57±22.28 | 161.41 | 8.790 s / 26.132 ms | 2.001 / 79.34% |

12→24 卡按同每卡并发从 C64→C128，吞吐 `3930.44/1942.67=2.023` 倍，GPU 翻倍时每卡 output tok/s 约 **+1.16%**；goodput `3.136/1.468=2.136` 倍。16→24 卡从 C96→C144，吞吐 `4120.98/2582.57=1.596` 倍，对比 GPU 1.5 倍，每卡约 **+6.38%**；goodput `3.167/2.001=1.583` 倍。前者新批 TTFT 较低，后者新批 TTFT 略高；后者逐请求联合达标率也略低（79.34%→78.70%）。这只是**历史已测工作点的算术比例**，并不是按同一固定软硬件单独增加 GPU 的扩展效率实验。固定 C64 对比多卡、或拿 16 卡 C128 对 24 卡 C128，回答的是不同问题，**不作为这里的同比扩容证据**。

关键限制：两组历史服务器及客户端均为 v0.29，本批服务器和客户端均为 v0.30；旧组来自早期 GovReport 精确 16K 前缀池，本批用[1024 条独立语义输入](../datasets/govreport-isl16384-exact-n1024.jsonl)，每档取前 4C，旧 12 卡 C64 每轮也是 256 条，但预热固定 256 条而本批 C128 为 256 条；旧 16 卡 C96 预热 192 条、每轮 384 条，新 C144 预热 288 条、每轮 576 条。旧 2P1D 的 D 每引擎 S32（单 D 名义 64），旧 3P1D/C96 的 D 每引擎 S48、Graph288（单 D 名义 96）；本批双 D 每引擎 S64、Graph384（D 整机名义 256）。旧 P budget16384、新 P budget16640，启动覆盖/补丁及背景不同。旧 3P1D/C96 特意使用**已修正 Graph288** 的 2582.57 tok/s，而非旧 Graph192 的 1480.51；拿后者作基准会虚增“扩容收益”。另有[16 卡 v0.30 3P1D/C128](v030-pd-16k-dp2-20260924.md)，但同每卡 C=8 应配 24 卡 **C192**，本次在 C160 停扫、**没有 C192**，不拿 C128 对 C128 冒充等负载，也不推算未测 C192 吞吐。这些改变足以影响斜率，数字只说明“目前没有看到明显次线性的历史同比并发扩容”，**不能证明 16K 适合或不适合 4P2D 的比例**。

特别地，4P2D/C144 Mean TTFT 9.190 s 虽未触及预定均值停扫线，逐请求联合达标率仅 78.70%；C160 Mean TTFT 已过 10 s 且 goodput 下降。若要判断“16K 是否应该用 4P2D”，需要在**同一 24 张 GPU、同六个四卡服务与相同镜像/数据/全局 C** 下，对比 4P2D 与 `2×(2P1D)`，后者两个分组各承担总 C 的一半；另可配对同 24 卡普通完整推理服务。不能将 4P2D/C64 与两个各 C64 的 2P1D 当作等并发。本次没有做这些新部署，因此 4P2D 与同资源替代方案的真实胜负仍未测出。

## 路由、Graph 与资源验收

- [八条 P→D 路由总核验](../../../experiments/dsv4-pd-24gpu-20260925/results/pd24-01/route-check.json)通过，每一正式轮的八条路径均有成功请求；每档各轮的 `routes.json` 保留实际分配，例如 [C128 第1轮](../../../experiments/dsv4-pd-24gpu-20260925/results/pd24-01/c128/round-1/routes.json)。每轮 P 与 D 的成功请求数分别等于全局 4C。C128 的四个 D 引擎在三轮分别完成 `[124,129,127,132]`、`[124,129,130,129]`、`[127,127,129,129]` 条，并非把全局 C128 乘以副本数。
- 各轮[引擎级计数样例](../../../experiments/dsv4-pd-24gpu-20260925/results/pd24-01/c128/round-1/engine-counter-deltas.json)证实 P 实际计算 4C×16384 个输入 tokens，D 远端 KV 命中同样多，**D 整段输入计算计数增加 0**。C128 每轮 D 总命中 8,388,608 tokens、NIXL 两个 TP rank 共 1024 次成功传输/约 88.26 GB；C64 分别为 4,194,304、512 次/约 44.13 GB。所有正式窗口的传输/通知失败、KV 过期与 preemption 增量均为 0；两 D 的四个 DP 引擎均有非零远端命中、传输字节、DSpark draft 和 accepted tokens。这是实测远端 KV 工作量证据，不是仅靠 HTTP 成功推断 PD 生效。

## 决策与边界

若目标是这批**固定配置下的最高已测整机吞吐**，C160 比 C144 高约 143 tok/s，但已触及事前停扫线，且逐请求 goodput 明显变差。C128～C144 是吞吐与延迟取舍的已测区域：C144 吞吐比 C128 高约 4.85%，Mean TTFT 由 8.104 升至 9.190 s，goodput 3.136→3.167 req/s 的差距与本批轮次波动接近；C128 是更留余量的候选，C144 是该停扫线内吞吐更高的候选。两者联合达标率均不到 95%，本次不因这个比率停扫，也不称其中任何配置为官方最优。没有 C176～C256 的实测数据，不能断言 C160 已达到硬件吞吐峰值。

所有原始日志、逐请求记录、代理事件和主机遥测仅保存在 45 本机[新 run-root](../../../experiments/dsv4-pd-24gpu-20260925/results/pd24-01/state.json)；此处的工作区相对链接在没有本地 `experiments/` 的克隆中不可用。分析导出由[本地脚本](../../../experiments/dsv4-pd-24gpu-20260925/scripts/analyze.py)重新验证 30 轮请求/token/路由后生成。结束时只按 owner 清理本次六服务与代理/客户端，46/47/48 全部 GPU 回到 0 MiB；未删除模型、镜像、历史结果或缓存，未 push。
