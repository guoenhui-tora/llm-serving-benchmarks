# DSV4 / RTX 6000D: 24 卡 5P1D 与 4P2D 的 C144 对照

## 结论与范围

同样的 24 张 GPU、全局 C144、GovReport 每条精确 16K 输入/1024 输出下，**5P1D 不是更高吞吐的选择**：三轮完整客户端窗口整机吞吐 **3452.64±35.25 output tok/s**，相对先前独立启动的 [4P2D/C144](pd-24gpu-16k-4p2d-20260925.md) **4120.98±8.80，低 16.22%**；goodput **2.784±0.035** 对 **3.167±0.037 req/s，低 12.09%**。增加一个 P 确实将 Mean TTFT **9.190→6.426 s**（低 30.08%），但只留一个 D 使 Mean TPOT **23.516→32.851 ms**（高 39.70%），请求平均/尾段完成时间也变差。因此观察到了 P 阶段变快、D 后续阶段变慢的明确权衡；不能据此断言 16K/1K 负载“根本不适合 2:1”，或把 5P1D 的低 TTFT 解释为整体性能获胜。

这是两次**不同服务启动批次**各三轮 quick 的本机对照，不是仅改变 P:D 比例的单变量实验。5P1D 把原 D1 所在的 48 前四卡改作 P4，P4→D0 因而变为同节点；路由、NIXL 路径、D 服务/DP 引擎数、各 D 引擎序列容量及 Graph 形状也随之改变。结果支持“当前 C144 的 P 供给影响 TTFT，同时第二个 D 对整机吞吐很重要”的方向性判断，不能把差异全部归因于其中任何单一机制。没有测 5P1D 的其他并发，也没有改动 4P2D 的既有扫描或 24 卡部署基线。

## 配置与预算

45 仅负责控制、代理与压测客户端，不计入 24 卡；46/47 各以前后四卡部署两套 P，48 前四卡 P4、后四卡 D0。各四卡服务均 TP2×DP2、EP on、DSpark K5、FP8 KV、V2 async、NIXL、关闭本地 prefix cache；P 各 DP 引擎 max-num-seqs=32、max-num-batched-tokens=16640、target/draft Graph 覆盖 192/160，单 D 各 DP 引擎 **S128**、budget **16384**、Graph **768/640**。单 D 整机名义容量 256，等于原 4P2D 双 D 合计名义容量 256；并不等于实际运行 batch，未缩 D token budget/容量。两组同用 `vllm/vllm-openai:v0.30.0` 的 image ID `sha256:8a69ffad015f138d7170c4ddc429e230a3bc1c1719f67e14324749df200a4b90`、同一 NVFP4 权重及本机 MXFP4 修复；服务端和客户端实际 argv 均使用该 image ID、`--pull never`。48 新 P4 使用 48 原 D 缓存中同哈希补丁与日志配置，P 内核预热可能比已有 P 更冷。

## 阶段与资源证据

从两个批次各三轮代理日志按请求 ID 和**各自正式窗口**匹配 576/576 个 `start`、`prefill_done`、`done` 事件。代理入口至 `prefill_done` 的逐轮请求平均时间：4P2D **8.460/8.422/8.540 s**，5P1D **5.495/5.759/5.442 s**；其后的代理 `done - prefill_done`：4P2D **24.692/24.770/24.733 s**，5P1D **34.563/34.523/34.181 s**。这些时间包括代理等待/通信、P 或 D 阶段，不是纯 GPU 算力耗时，也不是服务端 P 等待队列的秒数；前段缩短约 2.91 s、后段加长约 9.69 s，与客户端 TTFT/TPOT 方向一致。4P2D 的 P 引擎 waiting 抽样最高 15、5P1D 最高 10–11；两者都没有服务端逐请求 P 排队时间，因此不能把约 2.91 s 全部归因于 P 队列。

[五条 P→D 路由核验](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/results/pd24-5p1d-c144-02/route-check.json)全部通过：每条路径每正式轮 **114–116** 条，48 上 P4→D0 同节点每轮 **115** 条。每轮五 P 合计实际计算 **9,437,184** 输入 tokens，D 两引擎分别完成 288/288、283/293、286/290 条；D 远端 KV 命中等量输入 tokens，**整段输入重算计数 0**，NIXL 两 TP rank 合计每轮 1152 次成功传输、约 **99.29 GB**；D K5 draft/accepted 计数非零。各 DP 引擎均有成功请求，传输/通知失败、KV 过期和 preemption 增量均为零。样例[引擎计数](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/results/pd24-5p1d-c144-02/c144/round-1/engine-counter-deltas.json)与逐轮 route/counter 文件均保留。相比双 D/C144，D 两引擎抽样 running 峰值 **72/71**，waiting **3/4**，KV 使用最高 **33.95%**（双 D 四引擎 running **33/35/30/31**、waiting≤2、KV≤15.94%）。S128 并未在抽样中达到，**空闲序列槽不意味着 D 的逐 token 计算不忙**；每 30 s 抽样不能证明未观察到的短峰或给出逐步 Graph 命中率。

五 P target/draft CUDA Graph 全部实际完成 **13/13、14/14**；D S128 对应的[启动捕获](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/results/pd24-5p1d-c144-02/d0/startup-graph.json)实际 **35/35、34/34**，无 OOM。功能探测期间各 P JIT/TileLang 日志匹配 **8/8/8/4/4**、D **12**；完整预热 P3/P4 各 **4**，正式三轮各服务均 **0**。这些是日志匹配和 Graph 启动捕获，**不是逐步 Graph replay 比例**，预热时的事件不隐藏。正式轮 24 个约 30 s 资源样本中，18 个活动样本；P/D 显存约 **80,555–81,355 / 74,579–74,611 MiB/卡**，最高 GPU 利用率抽样 100%、温度 60°C、瞬时功率约 338 W。三节点均存在 `doca_spcx_cc` 背景 CPU，无法排除调度干扰。原有内核/连接器 warning 和完整服务日志保留在本机 run-root。

## 异常、复现与建议

第一次六服务启动 [失败状态](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/results/pd24-5p1d-c144-01/state.json) 已 READY 且 Graph 完整，但 8 条短功能请求仅能覆盖 10 个 P DP 引擎中的 8 个；旧 smoke gate 错误地要求每个 P 引擎都有命中，因此在 8/8 功能请求成功后停止，**没有预热或正式轮**。已保留[精确修正与反例](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/reports/attempt-02.md)：仅 8 条短功能探测免除逐 P 引擎命中，完整预热/正式轮仍严格检查 P/D 请求和 tokens、远端 KV、K5、错误与抢占；增加单测，其他配置/实际启动 argv/预算不变。第一次按 owner 清理后，第二次在**新 run-root** 跑完上述正式三轮；两批不能称作同一次启动，不把功能探测失败当性能重试。第二次[最终状态](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/results/pd24-5p1d-c144-02/state.json)为 `COMPLETE`、`changed_files=[]`、`cleanup_errors=[]`；只清理本次六服务、代理、客户端，46/47/48 的 24 卡随后回到 0 MiB，未删除 JIT 缓存、模型、镜像或历史结果。

复现需先获准使用对应节点，确认 GPU、NIC、NUMA/CPU、空闲端口、同 image ID/权重元数据/数据 SHA，准备本机旧 G2 `resolved.json`、MXFP4 修复和原 JIT 缓存；这些本机依赖与被 Git 忽略的 `experiments/` **不随报告归档**。原始[编排脚本](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/scripts/run.py)和[事前协议](../../../experiments/dsv4-pd-24gpu-5p1d-c144-20260925/reports/protocol.md)仅本机可用。以下为本次准备、校验、运行和分析的入口记录，**不是现在再次启动实验**：`prepare` 仅在第一次启动前生成不可覆盖的 plan；短功能门槛修正后重做 `offline`、单测、`preflight`，第二次以新 run-root 运行。原 plan/run-root 已占用，复测必须另建 owner/工作区/新 run-root，不能直接覆盖这批证据：

```bash
PYTHONPATH=src python3 experiments/dsv4-pd-24gpu-5p1d-c144-20260925/scripts/analyze.py
```

**当前建议：** 若关注 24 卡同负载 C144 的整机吞吐、goodput 和请求完成时延，继续选 **4P2D**；若仅关注 TTFT 且能接受约 16% 吞吐损失，5P1D 可作诊断线索，不应直接改线上配比。这个建议对**已配对的 C144 工作点**证据较强，对其他 C、跨批次稳定性以及 16K/1K 的普遍最优配比没有证明力；也没有测 `2×(2P1D)` 或普通非 PD 方案。
