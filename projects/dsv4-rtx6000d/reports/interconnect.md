# RTX6000D 互联报告阅读摘要

本页从用户提供的 [HTML 报告](interconnect.html) 整理，便于检索。**它不是原始逐次测量数据，也不新增测量。** 完整图表、三轮范围和方法以 HTML 为准；当前未收到独立原始 Markdown/CSV。

测试时间 2026-09-14–15，覆盖 45/46/47/48 四台八卡 RTX6000D。当前仓库整理只读取该报告，没有访问其他机器。

## 单机结论

GPU0–3 靠近 NUMA0，GPU4–7 靠近 NUMA2；近邻对为 `[0,1]`、`[2,3]`、`[4,5]`、`[6,7]`。PXB 为近邻桥接，NODE 跨同 NUMA Host Bridge，SYS 跨 CPU/NUMA 系统互联。

| 项目 | 报告结果 | 比较边界 |
| --- | --- | --- |
| 512 MiB CE 单向写 | PXB 约 53.5、NODE 约 32–33、SYS 约 28–30 GB/s | 与 SM 双向合计不是同一种测法 |
| 256 MiB AllReduce | TP2 约 7.2、TP4 约 15.7、TP8 约 21.1–21.7 ms | 同逻辑消息量，不能直接预测模型加速比例 |
| 多 TP 组同时工作 | 大部分变化小，个别 ReduceScatter 组下降约 2.5% | 未叠加 PP 推理流量 |
| PP 单对 256 MiB | 45/47：NODE 约 28.2–28.3、SYS 约 23.9–24.2 GB/s | 完整边界并发时每对约降至 11–13 GB/s；46/48 也约 11 |
| PP 小消息 | 4 KiB 单次约 28.5–29.8 µs | 路径差异不稳定，不是纯传播延迟 |

TP4×PP2 可让 TP 留在两个四卡区域内；TP2×PP4 使用最快的近邻组，但增加阶段边界。实际胜负仍取决于模型计算、气泡、批处理与通信重叠。报告假设同 TP rank 传分片，具体引擎的激活布局需单独核实。

## 多机结论

每台八个可用的 400 Gb/s RoCE 数据端口，近端 ConnectX-8/GDR 路径需由实际日志和端口流量验证。不能把端口理论带宽求和当作已测性能。

| 项目 | 报告结果 |
| --- | --- |
| 节点对八流单向持续传输 | 128–512 MiB 每流约 300–303 GB/s；六对节点没有明显弱项 |
| 单端口与多端口 | 单端口合计约 48 GB/s，多端口四对约 150、八对约 300；同时包含暂存路径差异 |
| 汇聚 | D=45/48：2P1D 约 304–305，3P1D 约 230–231 GB/s，下降约 24.3% |
| 两组不重叠节点对 | 测得带宽损失 −0.11%～+0.18%，该负载未见明显退化 |
| 四节点 collective | 部分 AllReduce/ReduceScatter、小消息 AllGather 波动较大，不能只用中位数精确预测 |

汇聚使用同步等量 Send/Recv；不是实际 KV 打包、NIXL/Mooncake 或完整 PD 服务。3P1D 的网络结果不直接决定最佳 P/D 实例与卡数比例。

## 方法与环境

驱动 580.159.04、CUDA 13.1.115、NCCL 2.29.2、nccl-tests 2.19.6、OpenMPI 4.1.9a1。每 GPU 一进程，绑定近端 NUMA CPU，三轮独立运行。该通信探针软件栈不能直接当作 serving 镜像的内部版本。

单机显式 `NCCL_P2P_LEVEL=SYS`、`NCCL_IB_DISABLE=1`、`NCCL_NET=Socket`、接口 lo；网络测试使用 IB/RoCE、GID index 3 和指定 HCA。是受控设置，不是默认 NCCL 行为，也不应未经验证直接加入 serving recipe。

图表给出三轮中位数与最小—最大，不是 P95/P99。MiB/GiB 使用二进制单位，GB/s 使用十进制；collective busbw 按通信类型和 rank 数归一，不等于物理链路速率。
