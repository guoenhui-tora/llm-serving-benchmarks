# 分离式推理研究方法

PD分离让独立实例分别承担prefill和decode，并在两者之间交接KV。[DistServe（OSDI 2024）](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)说明了按TTFT、TPOT目标分别配置两阶段资源与并行方式，并以满足延迟目标的请求率评价系统。本页的单侧压测与端到端配对是实践流程，不是直接照搬论文的实验协议。

1. **固定负载与测量口径。** 明确模型、镜像与客户端、权重和tokenizer、真实请求集、输入/输出长度、GPU总数、全局并发、到达方式、完整客户端计时窗口及延迟目标。后续单侧实验用于缩小候选，是否值得分离则需要单独的整机对照。
2. **单侧筛选P。** 用真实长度输入、尽量短的输出（例如1 token）和关闭本地前缀复用的负载，对比实例拓扑、EP、token预算和近端通信。记录请求供给、排队、实际输入计算与资源占用。prefill-only仍有生成及调度开销，却不包含远端KV交接和D排队；它提供候选，不能直接预测完整PD的TTFT。
3. **单侧筛选D。** 在相同GPU总数与全局并发下，用共享真实前缀降低重复prefill，比较实例边界及并行拓扑；多实例应同步计时，整机吞吐为输出总tokens除以计时窗口的并集时长。逐请求核对前缀命中及仍在本地计算的输入tokens，不能把decode-only写成零prefill。核对各引擎容量、KV使用、running/waiting、抢占、JIT和实际Graph捕获；若使用投机解码，分别按每引擎容量检查target/draft Graph形状。
4. **回到完整PD验证。** 逐请求核对P→D路由、远端KV命中、D无整段输入重算、成功数与输入输出tokens。保持同一真实负载、客户端入口和计时口径，对单侧筛出的候选做端到端对照，同时观察P排队、D执行批量、JIT、Graph及资源背景。更快的单侧服务可能改变另一侧的排队，不能把单侧收益直接当成整机收益。
5. **选择PD并发。** 固定服务配置，仅改变客户端全局并发；预先规定预热、每档请求量、重复数、超时和停扫条件，保留异常轮次。报告完整窗口吞吐、TTFT/TPOT、尾延迟与逐请求达标goodput，找到符合目标的工作点。
6. **判断是否值得分离。** 例如固定同一批24张GPU，分别部署多个聚合式实例和一组P/D实例，两边都由一个全局入口分发请求。配对时固定模型、镜像与客户端、真实请求集、输入输出长度、到达方式、全局并发、计时窗口和延迟目标；入口路径若无法一致，应记录差异。聚合式服务可以采用适合自身的容量和预算，不必照搬P或D的参数。同一并发点比较整机吞吐、TTFT、TPOT和逐请求达标goodput，再比较各自在延迟目标内能承载的请求率；不能将单个服务的吞吐乘以实例数充当聚合式实测。没有这样的配对，就只能说哪种已测PD配置更好，不能说PD优于聚合式推理。
