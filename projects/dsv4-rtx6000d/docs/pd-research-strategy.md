# PD 分离研究策略

**这是一套从本项目试错中提炼的下次研究流程，不是声称现有两项负载依次按此流程完成。** 固定模型、权重、镜像/客户端、输入输出长度、真实请求集、GPU 预算、负载口径及延迟目标；16K/1K 与 24K/2K 应分别开展，不跨负载排名 tok/s。

1. **聚合式推理分支。** 测独立四卡实例和同节点多实例的整机扩容；选定一套可正常运行的聚合式服务参数。与 PD 配对时保持 GPU 总数、真实请求、全局并发、客户端窗口和 SLO 相同，不用单四卡吞吐乘实例数代替整机实测。聚合式服务无须被迫同时采用 P、D 不同的 budget 或容量；结论限定在所选聚合式基线，不宣称压过所有可能的配置。[早期聚合式推理参照](aggregated-serving.md)不等于当前 v0.30 的配对结果。
2. **单侧筛选 P。** 以真实长度输入、输出 1 token、无本地前缀复用检查四卡候选的供给、排队、TP/EP 通信和预算形状；只在有意义的档位改变并发。prefill-only 仍包含采样/投机准备，却没有远端 KV 注册、交接和 D 排队。16K 的 EP 与 PHB 定位、24K 的近 8K budget 初筛用于生成候选，不能将 req/s 乘 P 数直接预测 PD TTFT 或宣布数学最优。
3. **单侧筛选 D。** 固定 GPU 数、整机名义容量、真实输入前缀和全局并发，测不同实例边界、DP/TP、K5 target/draft Graph 覆盖、各引擎 running/waiting 与输出吞吐。[八卡 16K decode-only](decode-only-8gpu-20260925.md)只比较该工作量下的 D 候选；缓存命中仍计算约 256 输入 tokens，不是零 prefill，也不能替代真实 P→D KV 传输。
4. **完整 PD 验证。** 先验收 P→D 路由、KV 命中、D 无整段输入重算及真实工作量，再配对测单侧候选，检查 P 排队、D 批量、抢占、Graph/JIT 和资源背景。预算与 PHB 的单侧方向须由端到端实验确认；更快 D 未必改善闭环负载的 TTFT。之后只在固定服务配置下扫全局并发，保留预定轮次和越线档。
5. **回答是否值得分离。** 在同一负载、总 GPU 数和全局并发下，将最终 PD 与相应聚合式基线比较完整窗口吞吐、TTFT/TPOT 和逐请求 goodput；相同 GPU 数时“每 GPU 吞吐”只是在整机吞吐上除以同一个常数。当前两篇 v0.30 [24 卡 16K](pd-24gpu-16k-1k-study.md)和[16 卡 24K](pd-16gpu-24k-2k-study.md)给出 PD 内部优先工作点，尚未完成上述聚合式推理配对。

并发扫描前须分别核对 P、D 的每引擎容量、单步 token budget 与 Graph；全局 C 不等于任一引擎的运行 batch，也不要求 P、D 每一侧的名义容量都大于 C，详见[客户端并发与 vLLM 调度容量](../../../docs/benchmark-methodology.md#客户端并发与-vllm-调度容量)。研究过程中若出现旧镜像预热、Graph 覆盖或不支持的 token 预算，保存失败并缩小候选范围，不以放宽 gate 或只选较快轮次证明收益。版本特有的[mHC/JIT 历史经验](historical-jit.md)不是当前 v0.30 的启动依赖；具体模型、服务端口与代理见[PD 启动说明](pd-startup.md)。
