# 分离式推理：16 卡 3P1D 的 PP2/DP2 拓扑对照

本实验比较三个四卡 prefill 实例与一个四卡 decode 实例分别采用 TP2×PP2（下称 PP2）或 TP2×DP2（下称 DP2）的效果。2026-09-24 的端到端结果涵盖 16K 输入/1K 输出和 24K 输入/2K 输出两种负载；服务端为 vLLM 0.30.0，**客户端仍为 v0.29**。这是早期实例拓扑的诊断对照，不是后续负载研究的最终配置，也不是只改变 PP/DP 一项参数的严格消融。

## 结论

- **16K/1K：D 使用 DP2 更有利于吞吐。** 保持 P 为 PP2、Mooncake 路径不变，D 从 PP2 改为 DP2，C128 吞吐从 2643.29 提升到 3063.72 tok/s（+15.91%），Mean TPOT 从 36.435 降到 29.377 ms；Mean TTFT 则从 8.801 升到 9.968 s。PP2 P＋DP2 D 的远端 KV 按层映射和两个 D 引擎均已实际验收。
- **PP2 P 的独立收益尚未证实。** 16K 混合组与全 DP2 组吞吐接近（3063.72 vs 3091.86 tok/s），但两组的 connector、P 容量和代理路径不同；PP2 的 prefill 阶段耗时更短，不等于整机性能更好，也不能据此断言 Mooncake 与 NIXL 等效。
- **24K/2K：已测全 DP2 组合优于全 PP2 组合。** C32～C80 四档均如此；C80 吞吐分别为 2759.73 和 2151.53 tok/s。24K 未测 P 为 PP2、D 为 DP2 的混合组，不能从 16K 推出该组合在 24K 下的表现。

## 对照条件

四个独立实例各占四张 RTX6000D：P 分别位于 46 节点后四卡、47 节点后四卡、46 节点前四卡，D 位于 48 节点后四卡；45 节点只运行代理和客户端。实例绑定各自近端 CPU/NUMA。模型为 `DeepSeek-V4-Flash-0731-NVFP4`，服务镜像 ID `sha256:8a69ffad015f138d7170c4ddc429e230a3bc1c1719f67e14324749df200a4b90`，客户端镜像 ID `sha256:c2914767605584b6d8f45686b82de173ecc99e781897aa3d0a66dacd72c51ae1`。服务均启用 EP、DSpark K5、V2 async、FP8 KV，关闭本地 prefix cache，并加载 v0.30 MXFP4 草稿修复。

| 实际测试的组合 | P：每实例名义容量 | D：16K / 24K 名义容量 | KV 路径 |
| --- | ---: | ---: | --- |
| P DP2 → D DP2 | 2 个 DP 引擎各 S32，共 64 | 2×S64=128 / 2×S40=80 | NIXL/UCX |
| P PP2 → D PP2 | 1 个 PP 引擎 S32 | S128 / S80 | Mooncake |
| P PP2 → D DP2 | 1 个 PP 引擎 S32 | 2×S64=128 / 未测 | Mooncake |

16K 的 P 每引擎 `max-num-batched-tokens=16640`，24K 为 24832；D 均为 16384。P 的 K5 target/draft Graph 覆盖 192/160；D 的 Graph 随每引擎容量设置：16K PP2 为 768/640、DP2 为 384/320；24K PP2 为 480/400、DP2 为 240/200。**同为 16 卡、相同 D 总容量，并不代表 P 的服务容量也一致。**

16K 原始 GovReport 输入每请求精确 16384 tokens，输出 1024 tokens；其历史请求集 SHA256 为 `025246b18d8ba7e1bc4d98c1a20b32b570860bb06a0baf0cea4ae97403d982e7`，**未随 Git 归档**，不能用后来提交的 16K 数据文件冒充相同请求集。24K 使用精确 24576 输入/2048 输出的 GovReport 请求，JSONL SHA256 为 `615edb29e5a171e8f4dc7679739437202cddf8d93887f7b9a7260bc9e6d68170`。两种负载均为 `temperature=0`、`ignore_eos`、无限到达率，C 是代理入口的全局并发。每档先预热 2C 条完整请求，随后三轮各 4C 条正式请求；吞吐按包含代理、P、KV 交接及 D 的完整客户端窗口计算。下表吞吐为三轮均值±样本标准差，其余指标为三轮均值。

## 端到端结果

### 16K/1K，全局 C128

| P | D | KV 路径 | 输出 tok/s | Mean TTFT，s | Mean TPOT，ms |
| --- | --- | --- | ---: | ---: | ---: |
| PP2 | PP2 | Mooncake | 2643.29±19.72 | 8.801 | 36.435 |
| DP2 | DP2 | NIXL | **3091.86±18.69** | 10.254 | **28.391** |
| PP2 | DP2 | Mooncake | 3063.72±9.41 | 9.968 | 29.377 |

三组 D 总容量均为 128，每轮 512 条正式请求。混合组相对全 PP2 组只保持了 P 拓扑与 connector 相同：D 从单个 PP 请求池变为两个 DP 引擎，闭环补发速度也随之变化，因此吞吐和延迟差异不能全部归因于 stage 计算。服务端计数显示，P 阶段耗时在全 PP2、混合、全 DP2 组分别为 2.595、3.040、4.647 s；这是请求阶段的墙钟统计，不是纯 prefill kernel 时间。D 排队均值依次为 1.226、1.577、0.277 s；不能直接把排队时间当作 KV 传输时间。

### 24K/2K，全局 C32～C80

| 全局 C | P/D 组合 | 输出 tok/s | Mean TTFT，s | Mean TPOT，ms |
| ---: | --- | ---: | ---: | ---: |
| 32 | DP2/DP2 | 1607.41±14.60 | 5.167 | 15.983 |
| 32 | PP2/PP2 | 1281.41±18.78 | 5.662 | 20.740 |
| 48 | DP2/DP2 | 2056.50±21.66 | 6.315 | 18.547 |
| 48 | PP2/PP2 | 1636.04±26.33 | 6.905 | 24.022 |
| 64 | DP2/DP2 | 2430.03±12.10 | 7.436 | 20.872 |
| 64 | PP2/PP2 | 1933.89±9.07 | 8.071 | 26.832 |
| 80 | DP2/DP2 | **2759.73±5.28** | **9.107** | **22.412** |
| 80 | PP2/PP2 | 2151.53±19.11 | 9.393 | 29.954 |

两组 D 总容量均为 80。C80 的 PP2 P 阶段耗时为 3.059 s，DP2 为 3.741 s，但前者 D 排队约 1.230 s、后者约 0.254 s；P 阶段的时间优势没有转化成更好的端到端吞吐或 TTFT。这里同时改变了 P、D 拓扑和 connector，无法把差异单独归给任何一项。

## 后续单侧验证

旧分析曾怀疑 PP2 D 的 stage 负载不均或固定的 43/85 请求分组拖慢 decode。之后在同节点同四卡、服务端与客户端均为 v0.30 的共享 16K 前缀、C128/1K decode-only 对照中，PP2 为 **3087.56±8.71 tok/s**、DP2 为 **3570.45±99.14 tok/s**：PP2 的 decode 工作路径确有吞吐劣势。不过 DP2 首轮出现 JIT 且吞吐逐轮上升，不能将 15.64% 差距解释成稳定上限，也不能直接与上面的端到端 tok/s 排名。

完整窗口的逐步请求 ID 记录显示，满并发纯 generation 常按 **60/68、62/66** 两组隔步轮换，而非始终 43/85。带 profiler 的短窗口曾见 43/85，但测量条件不同；排除 NCCL kernel 后的 stage GPU 活动重叠也不能把主模型计算、草稿生成、通信和等待分别计时。因此 **PP 后一 stage 是否为主瓶颈、改成非均匀分层能否获益，仍未证实**。

还曾只把 PP2 的 `--max-num-scheduled-tokens` 设为 384，decode-only 吞吐降至 **1832.12±12.68 tok/s**，并出现大量本地输入块分拆；该参数同时限制 context 和 decode，不能用这次负结果推断独立限制 decode 批次的收益。直接把整项 token 预算缩到 384 不应列为已验证的优化。扩大请求容量、同拓扑更换 connector、逐 layer 提前传输也都没有完成受控性能对照。

## 复现限制与数据

Mooncake 组合在固定镜像中可用，但本次还需[归档的 Mooncake 代理与观测组件](../patches/v030-pd-mooncake/README.md)：代理处理 transfer ID、bootstrap 元数据及 P→D 路由；观测组件用于验收，不是新的模型 forward 或 KV 传输算法。全 DP2 走 NIXL、PP2 相关组合走 Mooncake，NIC 与代理路径也不同；仅交换 `--pipeline-parallel-size` 并不能重建这组实验。所有正式轮均验收远端 KV 命中、D 无整段输入重算、零请求失败、零抢占及无已识别的正式 JIT；本机 decode-only DP2 的 JIT 例外已在上节说明。

本次端到端的[拓扑诊断逐轮 CSV](results/pd-pp2-dp2-topology.csv)保留完整批次与失败诊断行，**性能表只采用 `eligible=True` 的完成批次**。历史客户端版本及未归档的 16K 请求集使得当前 Git 检出不能逐字节复现全部结果；本篇给出当时的比较口径，不将后续版本或其他负载的数字混入同一对照。
